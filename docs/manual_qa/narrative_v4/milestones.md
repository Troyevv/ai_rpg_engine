# #40: значимые переходы и длинная история

```bash
RPG_DEV_TOOLS=1 python scripts/narrative_test_world.py --checkpoint milestones
RPG_DB_PATH="$PWD/data/dev-narrative-v4.sqlite3" python -m uvicorn backend.main:app --host 127.0.0.1 --port 8010
```

Повторный запуск loader создаёт новое прохождение и не меняет существующие сейвы.
Выберите возвращённый save ID. Используется тот же мир «Два берега», объединяющий
исходные состояния `family` и `residence-roles`. `base` и прежние checkpoints не меняются.

Checkpoint воспроизводит через StateResolver/committed_snapshot шесть подтверждённых
переходов до первого игрового хода и добавляет 80 обычных пакетов History. Поэтому
переходы уже находятся за пределом обычного 64-пакетного чтения. Не создаются
фиктивные игровые ходы UI или будущие механики #41/#42/#43. Начальное игровое
время — 2026-10-05 09:06, номер хода — 0.

| Исходное событие | Canonical состояние / ожидаемый milestone |
|---|---|
| Помолвка Тимура и Марины | `qa_new_engagement` историческая, `engagement` сохранён |
| Брак Тимура и Марины | `qa_new_marriage` историческая, `marriage` сохранён |
| Последующий развод | Этот брак closed/divorced, отдельный `divorce`; старый milestone не переписан |
| Переезд Кирилла | `qa_new_home` active в `qa_garden`, `qa_home_residence` closed; физически Кирилл остаётся в `qa_home` |
| Ася завершила школу | `qa_pupil` closed/graduated, `role_ended`; новая роль не придумана |
| Смерть Павла | `qa_pavel` dead; identity, родство и история сохранены, `death` |

Кирилл и Вера знают перечисленные события через подтверждённые testimony events.
Зоя не знает их; секреты исходного мира остаются секретами. В карточках должны быть
актуальные жизнь/родство/проживание/роли, а не состояние из старого milestone.

## Проверка индекса без зависимости от ответа LLM

Откройте в браузере `http://127.0.0.1:8010/api/saves/SAVE_ID/milestones`.
Замените SAVE_ID числом из loader. Результат — JSON только известных Кириллу переходов.

- `?actor_id=qa_timur&category=marriage` — один старый брак, хотя сейчас он закрыт.
- `?category=divorce` — отдельный развод.
- `?start_date=2026-10-05&end_date=2026-10-05` — переходы этого дня.
- `?limit=1&offset=0`, затем `offset=1` — разные страницы; чтение не двигает время.
- Переключить управление на Веру — те же известные ей переходы.
- Переключить на Зою — эти переходы отсутствуют, включая IDs/счётчики/скрытое имя.
- Вернуть Кирилла. Смена управления сама не создаёт `protagonist_transition`.

В «Контекст ведущего»/диагностике запроса milestone-блок ограничен релевантными
персонажами и бюджетом. Старый брак не должен возвращать Тимуру и Марине статус
супругов. Обсуждение будущей свадьбы не создаёт нового `marriage`.

## Игровая последовательность

1. Start → обычный разговор → перезагрузка страницы → следующий разговор.
   Состояние и прежние milestones сохраняются; новые обычные реплики не засоряют индекс.
2. Явно выбрать и установить завершение работы Кирилла. При принятом extraction
   `qa_job` закрывается; появляется ровно один `role_ended`. Другие роли не меняются.
3. Reload → regenerate с исходом без завершения работы: этот milestone отсутствует
   в новой версии. Вернуть прежний variant: milestone снова доступен. Rollback:
   состояние и набор milestones равны исходным. Соседняя ветка не видит чужой исход.
4. Установить официальную смену имени NPC: текущая карточка меняется; старые
   marriage/engagement summaries и исторические имена остаются прежними.
5. Обычный визит, диалог, эмоциональная реакция и Time Skip без установленного
   биографического перехода не создают milestones.

Ручная модель не обязана дословно повторять сценарий. Проверяйте принятые canonical
изменения и diagnostics. Автоматический `tests/test_milestones.py` воспроизводит
эти проверки без платных вызовов, включая 3000 пакетов, 120 лишних NPC,
причинную цепочку авария → condition/role/пропущенная встреча,
retry/save/reload/rollback/regenerate и старые структурированные History.

Birth индексируется только при установлении известной даты рождения; ребёнок не
«рождается сейчас» из факта о старом дне рождения. Настоящие birth/protagonist/advance
механики реализуются в своих следующих задачах, здесь проверяется только их
минимальная граница с индексом.

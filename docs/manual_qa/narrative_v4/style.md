# Narrative Style Contract (#111)

## Аудит и границы

Baseline: master `fc47f6c` (GenrePolicy #110 уже merged); архитектура #136 сохранена.
Старый открытый PR #89 не включён в master: это альтернативная, более длинная
инструкция, а не зависимость. Не сливать оба контракта без согласования.

`engine.run_job → context_builder.build_context → runtime_v3.context.build_context
→ NarrativeContextBuilder.build` обслуживает start/turn/pov/background и detailed
Time Skip. `long_term.run` вызывает тот же builder с kind=background.
`NARRATIVE_STYLE_CONTRACT` добавляется один раз в `NARRATIVE_CONTRACT` после
выбранного builtin/custom game/background prompt. Extraction использует отдельный
builder/контракт, Tabletop не затронут. Из старого Narrative contract убрана отдельная
дублирующая инструкция диалогов; шаблон game отсылает к общему контракту.

Regenerate/retry используют записанный контекст, не собирают его заново. Новый ход
содержит стиль один раз; его regenerate — тот же текст один раз. **Исторические
ходы до обновления сохраняют старый стиль при regenerate.** Переписывать их контекст
ради новой политики нельзя: это нарушило бы воспроизводимость. Следующий новый ход
получает новую политику. Сохранённые пользовательские prompts не переписываются;
авторский стиль уточняет общий, но не отменяет agency/Knowledge/canon. Произвольный
пользовательский текст не подвергается семантическому удалению повторов.

Нет новых model calls, литературных валидаторов, квот, состояния или миграций.
GenrePolicy меняет предпочтения, не авторизует события и не отменяет базовый стиль.
Контракт остаётся в защищённой системной части; существующий budget estimator
учитывает его размер. Переполнение core по-прежнему даёт явную ошибку, а не обрезает
канон/agency. Язык технической инструкции не задаёт язык игры.

## Ручная проверка на существующем мире #78

Загрузка/reset и отдельный сервер — по [README](README.md). Использовать checkpoint
`base`, затем при необходимости существующие `appearance`, `pacing` и `phone`. Не менять baseline и
не добавлять другой формат fixture. Каждый reset создаёт новое прохождение.

1. Начать игру, выполнить обычный ход, сохранить/перезагрузить и выполнить следующий.
2. Проверить оригинальный контекст в диагностике: один `NARRATIVE STYLE CONTRACT:`,
   один блок Genre (при заданном жанре), действующие agency/Knowledge/POV.
3. Повторить с пользовательскими game/background prompts, с разными жанрами и без
   жанра. Выполнить regenerate, rollback → новый ход и ветвление: история не
   переписывается; regenerate повторяет исходный контекст, новый ход — актуальный.
4. В режиме наблюдения и Long-term Advance проверить тот же стиль; не приписывать
   внешнему управляемому персонажу решения и не раскрывать сведения из другой камеры.

| Сцена / ввод | Что оценивать в тексте и каноне |
|---|---|
| Повседневность: «Спрашиваю Тимура, как прошёл день» | Индивидуальные реплики; уместные предметные детали, без каталога ощущений |
| Романтика: предложить разговор наедине | Подтекст и паузы без обязательного сближения, ответ/согласие игрока не сочинены |
| Несогласие: «Нет, я не согласен» | Различимые голоса; не обязательная терапия/примирение, не искусственная ссора |
| Напряжённое действие: реагировать на установленную угрозу | Краткость по темпу, без нового канонического исхода ради красивой метафоры |
| Телефон / сообщение через существующий канал | Голос/текст вместо невидимых улыбок, одежды и комнаты; remote ≠ presence |
| Упоминание отсутствующего NPC / невидимый NPC | Нет новой камеры, раскрытия тайн, мысленного портрета без доступного знания |
| NPC с пустой внешностью / известной внешностью | Не придуманы шрам/цвет глаз; известные черты использованы выборочно, не полная анкета |
| «Я жду»; молчаливый controlled actor | Нет его чувств, мыслей, прикосновений, решения ответить или сенсорных переживаний от автора |
| Повторить спокойную сцену 5–10 ходов | Нет одинаковых вздохов/взглядов, обрубков и метафор в каждой строке |

До/после каждого шага: canon меняется только принятыми событиями; нет новых
постоянных внешних признаков без события, Knowledge не транслируется всем, POV
не меняет control. Для проверки качества использовать одинаковые snapshot/input,
модель и настройки, несколько вариантов ответа. Оценивать отдельно: уместность
деталей, индивидуальность голосов, ритм/повторы, наблюдаемость/agency. Любое нарушение
последних двух границ — дефект, даже если проза красивая. Успешные unit tests
проверяют сборку и регрессии, **не доказывают качество текста DeepSeek**.

## Иллюстративные примеры, не результаты live DeepSeek A/B

Эти короткие редакторские пары показывают направление. Общий канон для каждой
пары одинаков; поведение NPC допустимо, но не обязательно. Игрок не получает новых
действий/эмоций. Физическое присутствие и канал заранее установлены.

**Кухня; дребезжащий холодильник, чашка и остывший чай установлены.**
До: «Тимур смотрит. Вздыхает. Берёт чашку. Он устал и хочет поддержки».
После: «Холодильник дребезжит, заглушая начало фразы. Тимур отставляет остывший чай.
— На работе? Прекрасно. Особенно когда начальник ушёл».

**Романтический разговор; Соня находится рядом.**
До: «Соня чувствует страх близости. Ей важно принять свои эмоции».
После: «— Я вообще-то хотела тебя увидеть, — говорит Соня и после паузы добавляет:
— Без всей этой компании».

**Телефон; связь прерывистая, собеседник за кадром.**
До: «Он нервно улыбается и проводит рукой по волосам у окна».
После: «— Только не клади… — связь съедает конец фразы. — Ты меня слышишь?»

**Напряжённая сцена; NPC и заклинившая дверь перед камерой.**
До: «Он боится. Дёргает дверь. Ещё раз. Очень страшно».
После: «Он наваливается на дверь плечом; та не поддаётся.
— Заклинило. Есть другой выход?»

Эти примеры не задают обязательные события, жесты, реплики или длину предложений.
Реальная модель может следовать инструкции непоследовательно; отдельного LLM-судьи
и автоматического ремонта прозы нет.

# #99 — браузерная регрессия с DeepSeek

## Stage B Retest → Stage C

После merge #211 и продуктовых #210/#213/#215/#217/#218 используется тот же runner.
`prepare-stage-c RUN --parent STAGE_B --reviewed` копирует историческую SQLite,
сохраняет ledger и один дополнительный лимит $2 на retest + продолжение вместе.
`preflight RUN --stage C` запрещает LLM-запросы. `run RUN --stage C --reviewed
--phase retest` повторяет только заранее записанные post-fix случаи. `--case` и
`--step` ограничивают группу и максимальный индекс, не сбрасывая прогресс.

После проверки canonical State/History/Knowledge/agency результат записывается в
`semantic-reviews/CASE.json` (`case`, `status=passed`, непустой `checks` со всеми true
и конкретными доказательствами). `review-stage-c RUN --case CASE --reviewed`
привязывает review к хешам retest. Только затем `run RUN --stage C --reviewed
--phase continue` допускает соответствующую группу; held-группы остаются закрыты.
Повторный запуск не повторяет существующие paid attempts. 120 новых action
reservations и 320 calls — верхние safety caps, не целевое число ходов.

Отрицательный Knowledge retest может иметь `expected_rejection=controlled_actor_unsupported`:
review дополнительно проверяет полную атомарность, финальную диагностику и валидный
temporal в сохранённом Extraction/repair. Исходный held result остаётся held;
это не разрешение повторить его и не утверждение о сохранённом ходе.
В текущем прогоне все шесть групп остановлены, `C.complete` отсутствует; см. #220–#223
и #226. Для semantic failure после saved job используется `stage_c.record_hold`:
явная запись `semantic-holds/CASE.json` с case/status=held/reason привязывается к
артефактам шага. `group-holds` проверяются по хешам до dispatch и блокируют только
соответствующую группу; API success не снимает такую блокировку.

[Отчёт Stage C](live99-stage-c-20261107.md) отделяет live результаты от offline
регрессий, unknown outcomes и непроверенных гипотез. Не использовать продолжение
Stage A/B вместо нового допуска Stage C и не копировать ledger с обнулением расходов.

## Отдельно разрешённый Stage B

После merge #202 Stage B использует тот же runner, browser actions, oracle и ledger.
Новый изолированный каталог получает SQLite backup последнего retest и ссылки/хеши
исторических результатов. Старый family-save остаётся в копии; для нового семейного
сценария loader #78 создаёт `pregnancy` (QA gestation = 1 день, это не обычная физиология).
План — 90 новых действий в шести группах, жёсткий предел — 100, включая отказы.
Готовность A не выдумывается: manifest фиксирует явное разрешение B после разбора A.

```bash
python -m devtools.live99.run prepare-stage-b /private/live99-stage-b --parent /private/live99-post204 --reviewed
python -m devtools.live99.run preflight /private/live99-stage-b
python -m devtools.live99.run run /private/live99-stage-b --stage B --reviewed
```

Разрешение B однократно привязано к каталогу в исходном ledger: **$2 дополнительных**,
100 новых действий и максимум 320 новых LLM attempts. Старые caps и receipts сохраняются;
новый каталог не возобновляет allowance. Денежное ограничение даёт консервативный
token ceiling `2e9 / 300 = 6_666_666`; весь provider input window по-прежнему резервируется
до каждого запроса. Неизвестный paid outcome останавливает весь B, продуктовый отказ —
только группу. Repair входит в бюджет, автоматического повтора оплаченных ошибок нет.
Stage C этим разрешением запрещён. Shared lock исключает параллельный запуск A/retest/B.

Phone начинает с одного явно разрешённого Retry прежнего held job без повторной отправки
сообщения. Campaign проверяет новый ход → regeneration → sibling → rollback → другую ветку.
LTA получает 4 calls: текущий Runtime использует пару Narrative/Extraction на группу;
прежний cap=1 не мог выбрать ни одной semantic group. Это не доказательство успешного
развития мира — проверять `unresolved`, History и реальные изменения после выполнения.
Последние действия выбираются только из реально показанных choices, с записью текста
до dispatch; отсутствие choices останавливает группу, а не создаёт повторные filler turns.

Для диагностированных QA-ошибок B есть узкий `review-stage-b --case CASE --step N --reviewed`.
Он не разрешает product retry. Поддерживаются: неотправленный Family LTA на 7 суток
(UI требует более 7, receipt задаёт 2 недели) и Crisis/Campaign context overflow **до**
Extraction. Для последних production builder должен подтвердить fit 40960; Narrative
и её request IDs остаются прежними. Изменённый save, новый job, уже полученная Extraction
или неизвестный ответ запрещают recovery. Исходные файлы не перемещаются/не заменяются:
receipt хранится в `recoveries/`, новая попытка — в `retries/001`. Каждая попытка входит
в прежний предел 100; ни allowance, ни счётчик не увеличиваются. Последующий resume
не выполняет существующую попытку заново. После QA commit требуются обычные adopt и preflight.


Стенд для Linux/WSL. Нужны Python 3.12, зависимости репозитория, собранный frontend и Python Playwright. Обычный E2E-сервер проекта использует тестовый провайдер. Этот стенд запускает собственный процесс с production `create_app` на свободном loopback-порту. Реальные действия отправляет Chromium. Сервер получает ключ только через окружение. Закрытие браузера и повторное открытие сохранения между шагами намеренны.

Первый платный smoke: [результаты и остановки 6 ноября 2026](live99-smoke-20261106.md). Default `context_length=32768` оказался недостаточен для Extraction newborn-family; поддержку моделью 1M нельзя считать автоматически выбранной настройкой приложения. QA теперь выбирает для family окно 65536 через обычные настройки UI, сохраняя output limits 2000/4096; другие группы остаются на 32768.

## Подготовка

Из корня ветки QA, на конкретном коммите. Используйте один каталог на весь согласованный бюджет A–C. Новый каталог создаёт новый независимый счётчик.

```bash
python -m pip install -r requirements.txt -r requirements-dev.txt 'playwright==1.62.0'
python -m playwright install --with-deps chromium
(cd frontend && npm ci && npm run build)
QA_DIR="$PWD/../live99-run"
python -m devtools.live99.run prepare "$QA_DIR"
python -m devtools.live99.run preflight "$QA_DIR"
```

`prepare` принимает только **новый каталог вне репозитория**, создаёт шесть прохождений штатным загрузчиком #78, задаёт профиль game для Flash. `preflight` открывает все шесть сохранений на desktop и mobile, сверяет состояние после reload, календарь, родословную, карточку, отношения, мир и список переписок. В этом процессе генерация заблокирована до dispatch. Его результаты и ходы, уже присутствующие в fixture, учитываются отдельно от live. Альтернативный уже установленный Chromium задаётся через `PLAYWRIGHT_EXECUTABLE_PATH`.

## Платный запуск

Перед запуском сверьте действующий [тариф Flash](https://api-docs.deepseek.com/quick_start/pricing/). Резерв рассчитан на максимальные цены $0.30 за миллион входных токенов и $1.20 за миллион выходных. При повышении тарифа остановитесь и пересчитайте пределы. Получение списка моделей с настоящей авторизацией выполняется на старте каждого live-процесса. При отсутствии `deepseek-flash` приложение не запускается.

Установите `DEEPSEEK_API_KEY` в окружении процесса. Для локального интерактивного запуска в Bash можно ввести значение без эха. Отключите трассировку команд прежде, чем вводить ключ.

```bash
set +x
read -rsp 'DeepSeek API key: ' DEEPSEEK_API_KEY; echo
export DEEPSEEK_API_KEY
python -m devtools.live99.run run "$QA_DIR" --stage A
unset DEEPSEEK_API_KEY
python -m devtools.live99.run report "$QA_DIR"
```

Браузерный процесс запускается без ключа. Все платные вызовы, включая дочерние стадии, repair и continuation, проходят через обычный DeepSeek transport с отключёнными SDK retries. Перед обращением к провайдеру общая SQLite-транзакция резервирует целое окно 1 048 576 входных токенов и запрошенный максимум вывода. Финальный usage уменьшает резерв после завершения стрима. Потерянный ответ или аварийное завершение сохраняют резерв. Потолок на каталог — 320 попыток, 3 млн токенов и **$2 суммарно**, действует самый ранний предел. Консервативное резервирование может остановить запуск раньше.

| Группа | Checkpoint #78 | Что проверять на свежей истории |
|---|---|---|
| Повседневность | initiative | Действие игрока, диалог, инициатива и направленные чувства с источником |
| Семья | newborn-family | Созданный до старта ребёнок, дата рождения и два родителя, отношения, разговор после родов |
| Кризис | milestones | Сохранение смерти Павла, последствия и добровольная смена управления на Веру |
| Знания | knowledge | Секреты, устаревшее убеждение, адресаты и свидетели, источники Knowledge |
| Долгая кампания | long-term | Новый ход, альтернативный ответ из исходного контекста, переключение варианта и rollback, LTA |
| UI и телефон | phone | Адресная отправка через телефон, сообщения, отделение от физической сцены, уведомления и reload |

Для последующих шагов агент чередует тематические действия с выбором вариантов из реально показанных моделью. Заранее подготовленное рождение/смерть проверяет последствия. Отдельно фиксируйте в отчёте, если само событие состоялось в live-истории. Наличие кнопки, заданный игроком вопрос или наличие стартового факта сами по себе не доказывают достижение сюжетного исхода.

Лимиты этапов накопительные на каталог. До 20, 100 и 700 **действий** соответственно, включая детерминированные операции. Число сохранённых ходов с подтверждённым обращением к DeepSeek считается отдельно. Для B сначала прочитайте результаты A и разберите подозрения. Для C требуется дополнительное разрешение владельца бюджета после анализа качества B. Флаги не увеличивают денежный лимит.

```bash
# В окружении запуска снова требуется DEEPSEEK_API_KEY.
python -m devtools.live99.run run "$QA_DIR" --stage B --reviewed
# Только после явного подтверждения.
python -m devtools.live99.run run "$QA_DIR" --stage C --reviewed --approved-full
```

## Checkpoint и доказательства

### Продолжение после QA-исправления

Используйте исходный каталог с обоими SQLite, manifest и артефактами. **Не переписывайте manifest SHA.** Сначала commit проверенных QA-изменений, затем `adopt` разрешает только изменения внутри live99 QA-кода, его тестов и документации; product diff или грязный checkout блокируют запуск. Receipt сохраняет исходный SHA, новый QA SHA, хеши исходных доказательств, action count и денежные резервы. При последующем запуске потеря/изменение исходных доказательств или расходов блокирует dispatch.

```bash
python -m devtools.live99.run adopt "$QA_DIR" --reviewed
python -m devtools.live99.run preflight "$QA_DIR"
# Только для установленного false positive sequence=0, без генерации:
python -m devtools.live99.run recheck-saved "$QA_DIR" --case social --step 0
python -m devtools.live99.run recheck-saved "$QA_DIR" --case crisis --step 0
python -m devtools.live99.run recheck-saved "$QA_DIR" --case phone --step 0
# Только для family: завершён Narrative, Extraction ни разу не отправлялся.
python -m devtools.live99.run retry-extraction "$QA_DIR" --case family --step 0 --stage A
python -m devtools.live99.run run "$QA_DIR" --stage A
```

Все browser-команды используют установленный `PLAYWRIGHT_EXECUTABLE_PATH`, если он нужен. Только две последние команды требуют ключ и могут расходовать бюджет. `retry-extraction` сначала проверяет неизменность save, единственный исходный job, завершённый Narrative и отсутствие любой попытки Extraction; использует production context builder для проверки окна и остатка бюджета. Затем нажимает штатную кнопку Retry. Исходный оплаченный Narrative остаётся тем же; новые запросы разрешены для отсутствующей Extraction и её штатного repair. Уже полученная Extraction, неизвестный исход, изменение save или существующая попытка retry блокируют автоматический повтор. Продуктовый `continuity_external_decision` отслеживается в [#203](https://github.com/Troyevv/ai_rpg_engine/issues/203) и остаётся остановкой группы.

`result.json` исходного отказа не заменяется: recheck добавляет связанный хешами `verified.json`, Retry пишет `retries/001/` с собственными before/after, intent и diagnostics. Отчёт дедуплицирует сохранённые request IDs того же job. Исходный preflight остаётся на месте, новые записываются в `preflights/<QA-SHA>.json`, предыдущие отчёты архивируются.

В исходный `budget.sqlite` добавляется таблица `qa_actions`: прежние intent (включая архивные) импортируются один раз. Каждое новое действие и Retry резервируют место **до dispatch**. Удаление файлов и перезапуск не возвращают место; Retry тоже входит в общий предел 20 для A. Recheck/reload/настройки без игрового действия в этот счётчик не входят. Денежная таблица не очищается. `A.status.json` отделяет остановленные группы и исчерпание action budget; `A.complete` появляется только при успешном прохождении всей матрицы. Достигнутые 20 действий не означают, что продуктовые ошибки исчезли.

Повторите ту же команду на том же SHA и каталоге. Готовые шаги пропускаются. Незавершённый или ошибочный шаг останавливает свою группу, остальные могут продолжаться. Для отдельной группы есть `--case knowledge`. Не удаляйте папку шага и счётчик расходов ради повторной отправки. После проверки неотправленного действия `recover-unsubmitted "$QA_DIR" --case NAME --step N` архивирует попытку, только если текущий snapshot совпадает с исходным и для save не зарегистрирован новый job. Начатую платную попытку стенд автоматически не повторяет.

`report.md` содержит шаги, статусы и расходы. В каталоге шага находятся intent с SHA и отметкой времени, полные before/after snapshots, список изменённых полей и ID, текущий узел History, ответ, попытки Extraction/repair, предупреждения Resolver, UI-проекция и видимый текст. При сбое сохраняется снимок экрана. Исходную SQLite и локальный каталог держите закрытыми: в них авторская перспектива и тайны вымышленного мира. Публикуйте только минимальный вычитанный фрагмент, нужный для воспроизведения.

Для разбора каждого шага сопоставьте текст сцены, извлечённые факты, источники знаний, принятые изменения, компоненты UI и следующую сцену. Отдельно проверьте agency, личную информацию, возраст, владение, актуальность целей и непрерывность истории. Автоматические проверки структурных инвариантов и отображённого текста не оценивают литературный смысл. Различайте **подтверждённый дефект**, **подозрение** и **качество повествования**. Для дефекта укажите severity, подсистему, SHA, fixture, шаги, expected/actual, before/delta, History, Extraction/Resolver, при необходимости скриншот. Найдите дубликаты среди открытых и закрытых Issues и PR до заведения задачи.

### Явный повтор после продуктового исправления #204

`retest` не является этапом B/C. Он требует merged `57c173d` и чистый checkout,
копирует сохранения SQLite backup API, проверяет точное равенство checkpoints
после загрузки новым Repository, сохраняет ссылку и хеши исходного каталога.
Исторические игровые БД и evidence не редактируются. `budget.sqlite` нового
каталога — ссылка на **тот же** исходный ledger; блокировка также общая.
Дополнительный предел $0.50 фиксируется один раз относительно консервативного
расхода (peak, cold cache). Повтор команды/новый каталог не обновляет allowance;
общий предел $2 продолжает действовать. Неизвестный расход сохраняет полный резерв.

```bash
python -m devtools.live99.retest prepare /private/live99-post204 --parent /private/live99-original
python -m devtools.live99.retest preflight /private/live99-post204
python -m devtools.live99.retest run /private/live99-post204
python -m devtools.live99.retest audit /private/live99-post204
```

План ограничен шестью новыми действиями: Knowledge — явный Retry исходного вопроса Вере,
следующий ход, regeneration, выбор исходного варианта, rollback; Phone — один
явный Retry исходного ошибочного job. Принятое чтение сообщения Runtime должен
использовать повторно; повторная генерация отклонённого решения разрешена именно
этим retest. Нет повторной отправки исходящего сообщения. Группа с ошибкой
останавливается; существующий intent никогда не исполняется автоматически снова.
Старые счётчики сохраняются, новые действия прибавляются к ним. Resume после
завершения/остановки не создаёт платных запросов. Наличие успешного preflight,
ключа, immutable evidence и прежних денежных записей проверяется до dispatch.

Для двух доказанных ошибок QA-навигации до dispatch доступен `review-unsubmitted`.
Он сравнивает jobs, requests, ledger и snapshots с исходным checkpoint; только при
полной неизменности создаёт отдельное разрешение на две попытки в `retries/001`.
Исходные intent/result остаются на месте и учитываются в общем числе действий.
Повторное review запрещено. Это восстановление QA-навигации, а не повтор ошибки Runtime.

Если именно post-#204 Knowledge Retry остановился при построении контекста до
нового dispatch, `review-context` измеряет production builder на 40960 токенах.
Он требует неизменный snapshot, сохранённую Narrative и отсутствие новых платных
запросов Knowledge; создаёт отдельный receipt и `retries/002`, добавляя одну
резервацию действия, без возврата старых. Нельзя применять к уже полученной
новой Extraction. Семейное окно 65536 и output caps 2000/4096 не меняются.

### Дополнительный checkpoint Crisis в Stage B

После полного прохождения исходных 15 Crisis шагов можно явно добавить покрытие
недееспособности из существующей `family-incapacitated` fixture:

```bash
python -m devtools.live99.run prepare-crisis-extension /private/live99-stage-b --reviewed
python -m devtools.live99.run run /private/live99-stage-b --stage B --case crisis --reviewed
```

`crisis-extension.json` фиксирует отдельный save и девять действий: начало сцены,
явная смена героя на Веру и вопросы о помощи, заботе об Асе, документах и сообщении
близким. Исходный Crisis save, plan и результаты остаются на месте. Используются
те же `step`, browser, oracle, budget и action ledger; лимиты не обновляются.
Death oracle требует сохранения **уже установленной** смерти, а не выдумывает её
в fixture недееспособности. Для обеих сторон этого условия есть регрессионные тесты.

# Narrative: тестовый мир для Epic #36

Issue #78 предоставляет инфраструктуру разработчика для последовательной эволюции
текущего Narrative Runtime. Название каталога — план эпика, **не новый runtime**:
игра по-прежнему использует существующий Initial World State и Runtime v3.
Это не демо-кампания или tutorial для игроков. Все данные вымышлены.

## Загрузка / reset

Из корня репозитория, после установки обычных зависимостей проекта:

```bash
RPG_DEV_TOOLS=1 python scripts/narrative_test_world.py
```

PowerShell:

```powershell
$env:RPG_DEV_TOOLS = '1'
python scripts/narrative_test_world.py
```

По умолчанию используется **отдельная** база `data/dev-narrative-v4.sqlite3`.
Команда намеренно не наследует `RPG_DB_PATH`. При необходимости явно задайте
`--db /absolute/path/to/dev.sqlite3`. Без `RPG_DEV_TOOLS=1` команда завершается
до открытия БД. В приложении нет нового HTTP endpoint, кнопки reset или импорта
devtools в production entry points.

Повтор той же команды означает reset: **всегда создаются новый workspace и новое
прохождение**, а не перезаписывается существующий save. Старое прохождение со всеми
ходами остаётся для сравнения. Команда не принимает ID сохранения/черновика и не
удаляет данные. Имя мира не используется как разрешение на перезапись. Одинаковый
immutable world может переиспользоваться обычной дедупликацией подтверждения.
Ненужные прохождения/черновики можно убрать штатными средствами приложения.

Ответ команды — JSON с `database`, `world`, `save`, `workspace`, `version_id`,
`fixture_version` и `checkpoint`. Сохраните его в протокол проверки.

Запустите **отдельный dev-сервер** на этой же БД; например, после `npm ci` и
`npm run build` в `frontend/`:

```bash
RPG_DB_PATH="$PWD/data/dev-narrative-v4.sqlite3" python -m uvicorn backend.main:app --host 127.0.0.1 --port 8010
```

PowerShell:

```powershell
$env:RPG_DB_PATH = "$PWD/data/dev-narrative-v4.sqlite3"
python -m uvicorn backend.main:app --host 127.0.0.1 --port 8010
```

Откройте `http://127.0.0.1:8010`, выберите Narrative, затем в библиотеке мир
**«DEV · Narrative QA · Два берега»** и самое новое «Новое прохождение».
В инспекторе «О мире и сохранении» номер прохождения должен совпасть с `save`
из CLI. После reset обновите библиотеку и выберите новое прохождение: уже открытая
вкладка намеренно остаётся на прежнем save. Не редактируйте localStorage вручную.

CLI не вызывает LLM. Для ручных ходов настройте провайдер штатным способом;
автоматические тесты подменяют только ответы провайдера. Русская художественная
проза fixture соответствует текущему русскоязычному интерфейсу. ID, проверки
ссылок и assertions canonical-семантики не зависят от текста LLM.

Draft scene ID — `qa_opening`. Draft location IDs заданы в builder. При обычной
миграции location IDs вычисляются существующим `identity('location', name.casefold())`;
не меняйте мигратор ради сохранения draft ID и не используйте UI `view:*` как
canonical ID. `Repository(...).get_snapshot(save_id)['world_state']` позволяет
проверить authoritative состояние; `GET /api/saves/{save}` даёт обычную UI-проекцию.

Детерминированы сущности и начальное canonical состояние. DB IDs, UUID workspace,
history pointers и служебные created_at — обычные метаданные хранения, не игровые
даты. Текст и результат реальной LLM после старта не обязаны повторяться побуквенно.

## Сценарии и автоматическая проверка

Выполняемые сейчас сценарии: [base.md](base.md), [calendar.md](calendar.md). Будущие commitments,
life-state, pregnancy, phone и long-term сценарии пока **не реализованы** и не
считаются пройденными. Их добавляет соответствующий child issue.

```bash
python -m pip install -r requirements.txt -r requirements-dev.txt
python -m pytest -q tests/test_narrative_test_world.py
python -m pytest -q
```

Smoke проходит через production `Repository.create_workspace → import_draft(json)
→ confirm_draft → migrate_snapshot → begin_job/run_job → commit`, открывает БД
заново и выполняет следующий обычный ход. Также проверяет варианты и откат.
Hypothesis проверяет ограниченные последовательности reset/reload/turn с сохранением
всех прежних saves. Не подключайте этот мир ко всем unit-тестам: маленькие domain
fixtures остаются отдельными. В полном наборе есть независимые Tabletop проверки.

## Контракт расширения для каждого child issue

В каждом PR Epic #36 явно оцените четыре пункта: нужны ли новые данные base,
детерминированный checkpoint, ручной сценарий и автоматическая регрессия из него.
Если нужны — обновите их **в том же PR**, включая совместимость fixture со схемой;
не переносите ремонт в #46. В PR можно записать «не требуется» с причиной.

Исходник один: `devtools/narrative_test_world.py`. `build_fixture()` каждый раз
создаёт свежий supported Initial World State, затем вызывает обычные prepare/validate.
`load_fixture()` использует штатный import/confirm, включая runtime validation.
Нельзя внедрять snapshot через SQL ради обхода этих проверок.

Для состояния, которое долго достигать вручную, добавьте небольшую именованную
функцию-преобразование свежего base в `CHECKPOINTS`; результат должен оставаться
тем же поддерживаемым aggregate. `--checkpoint NAME` использует общий loader.
Если будущему checkpoint необходима реальная последовательность canonical
transitions, переиспользуйте production constructors/resolvers и проверяйте их
результат, не добавляйте второй формат сохранения. Не копируйте полный JSON мира.

При намеренном изменении baseline увеличьте `FIXTURE_VERSION`, обновите таблицы,
assertions и опишите отличие. Используйте стабильные ID/время, исключите случайные
имена, UUID сущностей и текущую дату. Для каждого checkpoint зафиксируйте исходную
версию base, преобразования и точные изменённые preconditions.

Каждый сценарий обязан содержать: fixture/checkpoint, точные предусловия, действия,
ожидаемые canonical/UI результаты, отрицательный инвариант, save/reload и
rollback/variant ожидания (либо объяснение неприменимости). Не помечайте ещё не
реализованную feature как доступную. Именованные ветки сейчас отсутствуют: используйте
существующие варианты ходов и откат; новый branch API к scope #78 не относится.

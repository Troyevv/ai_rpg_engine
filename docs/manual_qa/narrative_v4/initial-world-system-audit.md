## Confirmed causes and corrections

1. **Provider budgets were incorrectly applied to combined checkpoints.** Each
   ties response permits at most 200 objective and 200 directed records. The
   accumulator then validated all responses as another TiesPart, and LifePart
   repeated the same cap. Sixteen mutually connected actors already produce 240
   directed records. Every batch can be valid while assembly deterministically
   fails with `ties/relationships: too_long`.
   TiesAggregate now validates the combined records without a per-response count
   cap; LifePart, paused aggregate editing and the editor schema use this boundary.
   Individual responses retain their caps. Runtime models/invariants are unchanged.
   Dense 2/16/30-actor graphs (2/240/870 directed records) survive composition and
   canonical JSON reload. Existing sparse 30-actor and 100-actor pair-planning
   tests remain enabled. There is no truncation, dropping or averaging of ties.
2. **Assigned pairs are stricter than a participant list.** Both endpoints may
   belong to a batch but their pair may belong elsewhere. Existing pair predicates
   remain mandatory; schema endpoint enums now also narrow to the assigned batch.
   Allowed unordered pairs are canonicalized before checking; parent/adoption
   orientation and emotional directions are never sorted. Out-of-batch records
   are rejected, not reassigned or silently discarded. A model can still ignore
   an instruction: JSON mode is not enforcement of the supplied JSON Schema.
3. **Technical redundancy created needless failure opportunities.** Python already
   derives emotional and Knowledge map keys. Prompts now say so. Objective tie
   IDs may be omitted and are derived from their map key before namespacing; a
   supplied conflicting ID still fails. Phase identities are not deduplicated
   merely because their endpoints match.
4. **Some bad checkpoints survived until assembly.** Places now check location
   and organization cycles and organization/location references before characters.
   Character batches reject unknown physical locations. Life checks record IDs
   and character/location/organization references before lore. Background and
   Knowledge check IDs, holders, fact references and replacement facts before
   opening. Opening checks controlled/POV actor references. The same checks apply
   in composition and applicable paused editors. Runtime remains the final layer
   for cross-stage chronology, agency, family and knowledge invariants.
5. **Planning could allocate an impossible downstream roster.** Setting now
   rejects over 100 locations/organizations and cast tiers on noncharacters.
   Request schemas expose these restrictions, accepted Knowledge Fact IDs and
   typed references for circumstances/background/Knowledge/opening. No new
   narrative facts are generated by validation.

## Token and scaling assessment

Measured compact base JSON Schema UTF-8 sizes in this environment (before dynamic
IDs, source context and instructions): Blueprint 1,766 B; setting 1,600 B; places
3,113 B; characters 10,933 B; ties 2,295 B; circumstances 11,487 B; background
1,320 B; Knowledge 2,400 B; opening 6,209 B; advisory review 601 B. These are input
schema bytes, **not output tokens or provider usage**. Dynamic request schemas can
be larger. The global output cap was not increased.

- Pair batching bounds directed output per request. Explicit historical phases
  can still be verbose. Every truncated request retains actual usage diagnostics
  when supplied by the provider and requires explicit retry.
- Pair coverage remains exhaustive: `ceil(N*(N-1)/12)` calls when there is more
  than one batch. This is 4 calls for 7 actors and 73 for 30; it is a cost/latency
  risk for large casts, not a claim of linear scaling.
- Places, circumstances, background and Knowledge retain existing whole-stage
  requests. Their maximum collection sizes and unbounded canonical prose do not
  guarantee fitting the configured output budget. This audit adds independent
  exhaustion/recovery coverage, but **does not certify maximum-size live worlds**
  or introduce an untested partition/reconciliation architecture for these stages.
- Context retains explicit source notes and accepted data. Large source/cast cases
  can consume substantial input tokens. The existing estimator is heuristic;
  schema-byte measurements must not be presented as DeepSeek tokenizer results.

# Structured world preparation

## Existing architecture and reuse

The old Scenario → Markdown summary → parser → immutable world flow remains available under “Со Сценаристом”. `world_parser.py` knows legacy headings, character markers and explicit knowledge-holder markers; it cannot reliably infer knowledge holders or all free-prose facts. Imported source is retained in full, and the editor reports that limitation instead of inventing holders.

The new preparation flow uses the same `preparation_workspaces`, cancellable preparation jobs/SSE, provider/model settings, tracked usage, prompt revisions, `document_versions`/heads, runtime World State v2, save snapshots and `world_entities` projection. No parallel character, relationship, knowledge or scene tables were introduced. The new prompt is seeded by the existing idempotent prompt migration. Existing saves and response-variant snapshots are never rewritten.

A draft is a versioned existing World State aggregate in the document journal (`kind=world_draft`, owner=workspace ID). The workspace revision is the concurrency token; document ID identifies an immutable state version. Each patch, entity operation, generation and restore appends a version. Restoring creates a new head; it does not erase later alternatives. A reload reads the backend head. Confirm records an idempotency receipt (`draft_save`, owner=workspace:version) in the same transaction as the immutable world, save and world-entity projection.

## Lifecycle

Free idea, optional Scenario output, and legacy Markdown/text import converge in the editor. A new idea creates its preparation workspace automatically on submission. Quick creation sends the original idea directly to the world generator: it first develops an internal creative design brief (`draft_world_design`), then structures the combined original idea and brief as World State (`draft_world`). These are two tracked provider requests; incomplete output can need a conditional completion request. The internal brief is not a Scenario workspace step or an additional document version. The separate “Со Сценаристом” route still generates a scenario and can pass it to the same world generator; the legacy Scenario → summary workflow remains available there. Import uses no LLM request. Draft generation uses the user's chosen summary provider/model and existing cancellation path. The current job phase is persisted in the preparation job so SSE reports generation progress. Older drafts with scenario outlines retain their version history; a newly generated world no longer creates or carries an intermediate outline.

The generator develops usable biographies, setting, directed relationships, existing conflicts, character knowledge and an opening scene, both when given a short idea and when given a prepared Scenario. A complete world now needs the design and structuring requests; the existing continuation mechanism can make more calls when output is truncated. Initial generation explicitly asks for a distinct private fact per character, known to its owner, without revealing the fact to unrelated actors. Explicit requirements are constraints; initial-generation gaps are creative space, while intentionally unresolved mysteries stay unresolved. This creative license never applies to runtime state updates. The earlier bundled prompt contained a contradictory instruction that allowed facts/events only from user input and a scaffold with empty relationship/thread maps; both are corrected. On startup the bundled prompt is automatically versioned over the previous untouched default, using `prompt_upgrades` so user-customized and restored prompts remain unchanged. A separate `campaign.public_description` is intended for spoiler-free preview; the fuller `description` stays in author/GM context.

After generation, the backend checks for missing NPC motivation, an owned secret for every card, thin or missing relationships, missing threads, placeholder or short card fields, verbatim text copied from the original idea, and an invalid opening interval. The opening is synchronized with the declared world clock; if other essentials are missing, **one conditional supplemental generation** receives a compact brief and may only fill missing character details, motivations, secrets, relationship descriptions and threads. The supplement is a separately accounted `draft_world_completion` request. It stores secrets in the existing facts/knowledge model with optional `owner_id`; shared facts are not miscounted as every participant's personal secret. It does not rewrite the user's source or existing facts. If the model fails to complete the required fields, the job reports an error and the previous draft version remains intact instead of silently saving an incomplete world. Imported documents and manual edits are unchanged; existing generated drafts remain available. Deterministic checks cannot prove literary depth or respect for every subtle user constraint; real DeepSeek/local-model quality still requires sampling.

Structured generation asks for one complete JSON aggregate using the existing streamed provider pipeline and continuation handling. JSON continuations receive a JSON-specific instruction; Markdown continuation behavior remains for Scenario and summary. Raw JSON is accumulated on the server, excluded from public job snapshots, decoded and checked before recording a version. Invalid JSON leaves the previous version intact. Structurally incomplete worlds can be repaired as drafts but cannot start a game. Targeted generation applies only the returned `value` to an allowlisted field; extra top-level operations are rejected. Character regeneration changes its card only, retaining identity and world links.

Validation checks identities, directed relationship references, knowledge/fact/source links, scene participants and intervals, actor state, world-clock consistency, events and threads. Semantic checks are intentionally limited heuristics (for example age/profession); they are warnings, not a claim of exhaustive literary consistency. Explicit/creative/unknown semantics are instructions to the model; the runtime has no provenance enum and this change does not add a competing provenance system.

Confirm does **not** call an LLM or parse Markdown. It copies the selected validated aggregate into the existing save. Opening that game uses the existing Start action, GM, State Delta, transaction, choices and branch/regeneration flow. Campaign metadata is included in the existing GM-only context section; actor knowledge remains separately represented.

## API

All routes are under `/api/workspaces/{id}/draft`:

- GET: safe Player projection by default; `?author=true` explicitly requests complete author data.
- POST `/import`: revision and complete legacy/export text.
- PATCH: revision plus patch/add/remove/restore operation. Structural IDs cannot be patched. Deletion returns a dependency error instead of cascading.
- GET `/dependencies`: entity references for deletion/whole-character review.
- POST `/generate`: world/field/character task, provider config, instruction, expected revision; returns the existing job contract.
- POST `/confirm`: expected revision and immutable version ID; returns world/save IDs idempotently.
- GET `/export`: expected version ID and `format=md|txt`.

Player View is projected server-side: public facts, known facts, actor-owned directed relationships, public places, current scene and actor state are visible. NPC → actor relationships and plot threads are visible only when explicitly marked for that actor via `visible_to_ids`. Author View retains the full aggregate. The player receives the public campaign annotation, never the GM description or private plans. For older drafts with no thread visibility metadata the projection conservatively hides those threads until the author marks them as known; absence of a marker cannot establish a character's knowledge. The generator is instructed to put only actor-visible content into the public opening scene, place descriptions and visible thread descriptions. This is a presentation boundary in the existing local single-user app, not a replacement authentication system; unstructured prose cannot be proven spoiler-free automatically.

Exports contain readable Markdown plus a versioned integrity-checked payload preserving existing IDs, directionality and knowledge. Importing the unmodified export reconstructs exactly that state. If the readable part was edited externally, import refuses the inconsistent payload and asks to edit the original export in the editor; it never silently treats stale embedded state as authoritative.

## Verification

Backend tests cover import/export roundtrip, default projection, patch isolation, immutable references, dependency deletion, stale revisions, restore, duplicate-confirm protection, save isolation, semantic warning acknowledgement, streamed world/field generation and first-context fidelity. Existing backend tests cover old saves, branches, cancellation and provider behavior. Browser tests cover creation, Author/Player views, field editing, export, reload, confirmed save and first GM turn at 360/390/412/430 and desktop widths, with screenshots. Browser/model fixtures test the integration contract, not the quality of an actual paid LLM response.
